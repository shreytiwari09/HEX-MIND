# Put the team on one live mission screen

H.E.X Mind should replace "a mission page plus a nine-tab Observability page" with one mission workspace built from three things the 2026 tools agree on: a **persona roster** whose rows carry a live state icon, a one-line "now doing" sentence built from the latest real event, and an elapsed timer; a **plan board** of milestones and features that ticks over and stays visible when done; and a **drill-down drawer** that opens in place for one persona or feature, with Live, Steps, Changes and Checks tabs. Claude Code, Copilot, Lovable, Devin, Replit and Cline all converge on this shape, and none of them promises an ETA or percent-complete; they keep long runs from looking stale with elapsed counters on the current step, setup phases shown as steps, and summaries that refresh every few seconds. The observability tools (Langfuse, LangSmith, OpenSearch, CrewAI AMP, AgentOps) split views by *unit of analysis* (run, step, span), never by *data source*, so H.E.X's Callbacks, Schema checks, A2A, Messages and Trace tabs should collapse into one run view with type filters, kept behind a Developer toggle. For handoff, the local-first answer is not a GitHub App: H.E.X should export the worktree as a clean repo with `.env.example`, a lockfile, a CI workflow, Dependabot and a per-stack Deploy section, then, on an explicit click, push it with the user's own `gh` login to a **private** repo, so H.E.X never touches a GitHub token. Every recommendation below draws only on events H.E.X already records or can record, so none of it requires showing invented activity.

## Every 2026 agent product shows a roster with live state

The common way to answer "who is working on what right now" is a list of agent rows grouped by state. Claude Code's agent view groups sessions as Pinned, Ready for review, Needs input, Working and Completed, with a header that counts each, and every row has a **state icon whose colour and animation encode state, a one-line summary of current activity, and an age** ([Claude Code agent view](https://code.claude.com/docs/en/agent-view)). Working rows refresh their summary **at most every 15 seconds**, and a finished session's age **freezes at the run's duration** instead of counting on ([same](https://code.claude.com/docs/en/agent-view)). Cline's Kanban cards show "the agent's **latest message or tool call**" so progress is visible from the board ([Cline core workflow](https://docs.cline.bot/kanban/core-workflow.md)); Replit Agent 4 puts parallel tasks on a Drafts, Active, Ready, Done board with a **live status indicator** per thread ([Replit task system](https://docs.replit.com/core-concepts/agent/task-system)); Lovable's task card shows "the current step, the files being changed, the tools in use … and how far a multi-step implementation has progressed" ([Lovable agent mode](https://docs.lovable.dev/features/agent-mode)).

Two details matter for H.E.X's rules. First, Claude Code's summary line is **written by a Haiku-class model** from what the session says it is doing ([Claude Code agent view](https://code.claude.com/docs/en/agent-view)). H.E.X should not copy that by default: a model paraphrase of an agent's own claim is exactly the kind of evidence the "agent claims aren't evidence" rule excludes. The deterministic alternative is better and cheaper: build the line from the latest real event, for example "Backend · writing `api/routes.py` · F3" from a `write_file` tool call, or "Backend · waiting for model reply · 42 s" from a provider request that has started but not returned. If a model summary is ever added, it must be labelled as a summary. Second, nested work rolls up rather than multiplying rows. Claude Code subagents get no rows of their own ("a running subagent counts as working") ([Claude Code agent view](https://code.claude.com/docs/en/agent-view)), and Copilot collapses subagent activity by default behind a **"heads-up display" of what it is currently doing**, expandable to full output ([GitHub changelog](https://github.blog/changelog/2026-03-19-more-visibility-into-copilot-coding-agent-sessions/)). For H.E.X, that means one row per persona (PM, Backend, Frontend, Data, Designer, DevOps, QA, Reviewer, Security), with any researcher or tool sub-work folded into its parent's line.

The persona states should map one-to-one to real lifecycle events: **Working** (animated, only between a recorded start and end), **Waiting on another persona** (a handoff recorded but not yet picked up), **Needs you** (an approval or question pending), **Idle**, **Done** and **Failed**. Nobody in the surveyed set ships a separate heartbeat widget; liveness comes from the animated icon plus a line that changes ([coding agent live UI notes, Claude Code agent view](https://code.claude.com/docs/en/agent-view)). H.E.X can do one honest thing more: a small "last event 12 s ago" stamp per row, computed from the real event timestamp. That stamp never lies; if the backend stalls, the user sees the number grow, which is the truth.

## Long runs stay credible through elapsed time, not ETAs

None of the official docs for Cursor, Kiro, Replit, Lovable, Copilot, Devin or Claude Code promise an ETA or a percent-complete; they layer a checklist, a step stream and attention cues instead. Cursor introduced structured to-do lists so "long-horizon tasks [are] easier to understand and track" ([Cursor 1.2](https://cursor.com/changelog/1-2)), and in Cursor 3 fixed a bug where **todo cards disappeared once all todos completed** ([Cursor 3.0](https://cursor.com/changelog/3-0)), which shows that users want the finished plan to stay visible. Kiro marks tasks in-progress or completed in real time and runs a dependency graph as **waves: "Waves execute sequentially; tasks within a wave execute concurrently"** ([Kiro specs](https://kiro.dev/docs/specs/)), a close match to H.E.X's milestones of features. Lovable shows **credits used while the request runs**, then the final cost ([Lovable agent mode](https://docs.lovable.dev/features/agent-mode)). Claude Code shows "waiting 3m" on a blocked session and offers Verbose, Normal and Summary view modes ([Claude Code agent view](https://code.claude.com/docs/en/agent-view); [Claude Code desktop redesign](https://claude.com/blog/claude-code-desktop-redesign)).

The most transferable fix is Copilot's. Since March 2026 its session log shows **environment setup steps such as cloning and firewall start, so the pre-work phase no longer looks idle** ([GitHub changelog](https://github.blog/changelog/2026-03-19-more-visibility-into-copilot-coding-agent-sessions/)). H.E.X has the same dead zones: worktree creation, Docker sandbox start, dependency install, and above all the long silence of a single model call. Each should be a visible step with a real elapsed counter driven by the recorded start time ("Calling `<model>` for QA · 38 s"; "Installing dependencies in sandbox · 1 m 12 s"). That is factual, unlike an invented ETA, and it is the single change most likely to stop a run from looking frozen. When a step ends, its timer freezes at its true duration, as Claude Code's does.

Two further patterns fit H.E.X cheaply. Replit snapshots a checkpoint with a git commit "at feature completion and major milestones" ([Replit checkpoints](https://docs.replit.com/core-concepts/agent/checkpoints-and-rollbacks)), which H.E.X's worktree can mirror so the plan board's "Done" ticks are backed by commits. And Lovable lets users send follow-ups that it "picks up at its next natural stopping point", while Bolt queues prompts until the current build finishes ([Lovable agent mode](https://docs.lovable.dev/features/agent-mode); [Bolt prompt queueing](https://bolt.new/blog/prompt-queueing)); H.E.X's mission chat could queue a user message for the PM at the next feature boundary rather than blocking input during a run. Notifications complete the set: Claude Code fires them when a session needs input, finishes or fails, and puts "2 awaiting input" in the tab title ([Claude Code agent view](https://code.claude.com/docs/en/agent-view)). Notifications while the app is open fit H.E.X today; while it is closed they stay deferred under D53 and D57.

## Drill-down opens in place, and pairs each claim with its evidence

The surveyed tools never send the user to another page to inspect one agent. Lovable opens a Details panel **where the preview normally is**, with a Timeline tab (every step, including tool calls), a Changes tab (file changes) and "Hide details" to return ([Lovable agent mode](https://docs.lovable.dev/features/agent-mode)). Devin's Progress tab is one unified worklog in which **clicking a shell command jumps to that point in the session**, beside IDE, Browser and Preview tabs ([Devin session tools](https://docs.devin.ai/work-with-devin/devin-session-tools)). Claude Code's peek opens a panel on Space without attaching, shows the pending question, result or status, accepts an inline reply, and on attach posts **a short recap of what happened while you were away** ([Claude Code agent view](https://code.claude.com/docs/en/agent-view)). Cline's card detail shows a diff against the base branch with **checkpoints that scope the diff to specific message ranges** ([Cline core workflow](https://docs.cline.bot/kanban/core-workflow.md)), and Replit's task review screen shows "the work log, test results, and a live preview of the changes" with apply or dismiss ([Replit task system](https://docs.replit.com/core-concepts/agent/task-system)).

For H.E.X, clicking a persona row or a feature card should open a right-side drawer on the mission page with four tabs. **Live** streams that persona's model output and tool calls for its current feature (this is where today's single interleaved "live output" log is split per persona). **Steps** lists each action paired with its observation, the pattern an OpenHands design note describes as pairing every observation with its originating action so one card shows both ([enyst design doc, non-official](https://enyst.github.io/arch/agent-canvas-tool-visualizers.html)): `write_file` with path and size from git, `run_check` with exit code and output from the sandbox. **Changes** shows the git diff for the feature, scoped by step as Cline does. **Checks** shows the QA acceptance tests, reviewer and security results as recorded by the sandbox. This drawer is where H.E.X's evidence rule becomes visible: the agent's claim sits next to the git or sandbox record that confirms or contradicts it. A "while you were away" recap, assembled from the recorded events since the user last looked rather than written by a model, is a cheap addition when the user returns to a running mission.

## Nine observability tabs should become one run view with filters

Today the Observability page has nine tabs, Blackboard (the default), Agents, Callbacks, Schema checks, A2A, Messages, Topology, Trace and Audit (from `apps/desktop/src/renderer/src/features/observability/ObservabilityView.tsx`). Most are slices of one event stream by source. The trace products organise differently. Langfuse puts **Tree, Timeline and Graph tabs side by side on the trace page** ([Langfuse agent graphs](https://langfuse.com/docs/observability/features/agent-graphs)); OpenSearch's reference design has Agent Graph, Trace tree and Timeline where **"all three views share the same selection state"** and one colour per operation type (agent, LLM, tool, retrieval) is reused across them ([OpenSearch agent graph](https://observability.opensearch.org/docs/ai-observability/agent-tracing/graph/)); AgentOps puts a waterfall on the left and the selected event's exact prompt and completion on the right ([AgentOps dashboard](https://docs.agentops.ai/v2/usage/dashboard-info)). CrewAI AMP, the closest match to a page a non-expert can read, is one scrolling page with an **Execution Summary (tokens, requests, time, estimated cost), a Tasks & Agents table, an Execution Timeline and the Final Output** ([CrewAI AMP traces](https://docs-platform.crewai.com/platform/en/features/traces)).

Langfuse's July 2026 graph rebuild gives H.E.X a ready answer for Topology. Its **Aggregated mode** draws one node per step name with a counter such as `retrieve_docs (3/3)` and "shows an agent's overall shape"; its **Expanded mode** unrolls one node per call in execution order to follow a single run ([Langfuse changelog 2026-07-13](https://langfuse.com/changelog/2026-07-13-graph-view-modes)). H.E.X's static Topology is the aggregated view; the expanded view of the current mission is what is missing. Handoffs deserve first-class treatment as edges between persona nodes, as OpenAI's `handoff_span` and Datadog's "agent a task was handed off to" do ([OpenAI Agents tracing](https://openai.github.io/openai-agents-python/tracing/); [Datadog agent monitoring](https://docs.datadoghq.com/llm_observability/monitoring/agent_monitoring)). For volume, LangSmith **collapses repeated or parallel tool calls into one grouped row** and opens subagents as nested views ([LangSmith view traces](https://docs.langchain.com/langsmith/view-traces)), and Weave filters by agent, model, error status and attributes with colour-coded event types and inline ERROR badges ([Weave agent activity](https://docs.coreweave.com/weave/guides/tracking/view-agent-activity)).

The live dimension is where H.E.X has to design for itself. Most of these products are **after-the-fact trace viewers**: CrewAI AMP shows a per-task "running" status with no live view described, Langfuse's graph docs say nothing about live updates, and Arize's animated Agent Path is a replay of a finished run ([CrewAI AMP traces](https://docs-platform.crewai.com/platform/en/features/traces); [Langfuse agent graphs](https://langfuse.com/docs/observability/features/agent-graphs); [Arize agents](https://arize.com/docs/ax/observe/tracing/agents)). No fetched source documents a graph that highlights the active agent live. H.E.X can build one honestly: a persona node lights only on a recorded start event and settles only on a recorded end or error event, never on a timer. The audience split, by contrast, is well established: LangSmith pairs a simplified **Trajectory** view with a raw **Details** view ([LangSmith view traces](https://docs.langchain.com/langsmith/view-traces)), and Microsoft labels its DevUI as for debugging during development, not production ([MS DevUI tracing](https://learn.microsoft.com/en-us/agent-framework/devui/tracing)).

The resulting structure is shown below. Everything in the left column already exists as data; the change is where it lives.

| Today (Observability tab) | Proposed home |
|---|---|
| Agents | Mission page roster (default view) |
| Trace, Callbacks, Schema checks, A2A, Messages | One **Run** view (Developer toggle): tree / timeline / graph sharing one selection, with type filter chips (model call, tool, handoff, A2A, schema check, callback) and an errors-only toggle |
| Topology | The Run view's graph, with Aggregated (today's topology) and Expanded (this mission, live) modes |
| Audit | Run view filter plus a per-step link from the drawer's Steps tab |
| Blackboard | Hidden when empty for mission-runner missions; otherwise a Developer-view panel |
| (none) | Slim mission header: total cost, tokens and elapsed time, with per-persona and per-feature cost in the drawer |

Each step in the drawer should deep-link into the Run view filtered to that step, which closes the "two pages are far apart" problem without throwing away developer depth.

## Handoff means a clean private repo, pushed with the user's own login

The app builders all hand off through a hosted GitHub App: Lovable creates a new repo, **private by default**, and syncs both ways; Bolt creates a private repo, commits after each non-breaking change and polls GitHub every 30 seconds; v0 creates a private repo, commits to a working branch and merges through a PR on Publish, offering "Fix CI" when required checks fail ([Lovable GitHub](https://docs.lovable.dev/integrations/github); [Bolt Git](https://support.bolt.new/integrations/git); [v0 GitHub](https://v0.app/docs/github)). H.E.X is local and already runs git, so it does not need that machinery. The `gh` CLI does the whole job with `gh repo create <name> --private --source=. --remote=origin --push`, and non-interactive use requires an explicit visibility flag ([gh repo create](https://cli.github.com/manual/gh_repo_create)). H.E.X should detect `gh` and `gh auth status`, and only on the user's explicit Publish-to-GitHub click run that command, so the GitHub token stays in the user's own `gh` credential store and never reaches H.E.X's backend, renderer, logs or sandbox. Without `gh`, it shows the manual `git remote add` and `git push` steps. Making the repo public, which Streamlit Community Cloud's simplest path assumes, is a separate confirmation ([Streamlit connect GitHub](https://docs.streamlit.io/deploy/streamlit-community-cloud/get-started/connect-your-github-account)).

None of the builders document what their first commit contains, and the notes found no evidence that they generate CI ([handoff notes, v0 GitHub](https://v0.app/docs/github)). H.E.X can do better than they do. Before the push, it should run a handoff pass inside the worktree that produces one clean "Initial commit: `<app name>`" on `main`, without the agents' worktree history unless the user asks for it, and adds what the deploy docs agree a small repo needs. Lovable leaves secrets out of exports and users must recreate them ([Lovable export FAQ](https://lovable.dev/faq/code-export/export-download-code)), so `.env.example` lists variable names only. `npm ci` installs exactly the lockfile's versions, which makes a committed lockfile the basis of reproducible CI ([GitHub Docs Node.js CI](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)). Dependabot lives in `.github/dependabot.yml` with `version: 2` and supports `pip`, `uv`, `npm`, `docker` and `github-actions` ecosystems ([Dependabot options](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference)). A pre-push scan for secrets and files over 100 MB, which GitHub rejects ([Lovable GitHub](https://docs.lovable.dev/integrations/github)), runs on the staged tree, and the user approves the result as with any other apply.

The per-stack additions and the cheapest deploy targets come straight from host documentation:

| Stack | Files to add | First deploy target | What it needs | Caveat for the README |
|---|---|---|---|---|
| Streamlit | `.streamlit/config.toml` at repo root; `.streamlit/secrets.toml` gitignored plus an example; app runs from repo root with forward-slash paths ([Streamlit file organization](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/file-organization); [secrets](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/secrets-management)) | Streamlit Community Cloud, free | GitHub repo, `requirements.txt`, entrypoint; secrets pasted as TOML in Advanced settings ([deploy](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/deploy)) | Sleeps after 12 h without traffic; limits dated Feb 2024 ([manage app](https://docs.streamlit.io/deploy/streamlit-community-cloud/manage-your-app)) |
| React / Vite SPA | SPA rewrite file for the chosen host (`_redirects`, `vercel.json`, …); `VITE_*` documented as public, build-time ([Lovable external deployment](https://docs.lovable.dev/tips-tricks/external-deployment-hosting.md)) | Netlify, Vercel or Cloudflare Pages | Build `npm run build`, output `dist`, Node 22 | Netlify Free is 300 credits/month and a production deploy costs 15 ([Netlify plans](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/)) |
| FastAPI | `app` object in `main.py` or `app/main.py`; bind `0.0.0.0:$PORT` ([Vercel FastAPI](https://vercel.com/docs/frameworks/backend/fastapi); [Cloud Run quickstart](https://docs.cloud.google.com/run/docs/quickstarts/build-and-deploy/deploy-python-service)) | Render free or Vercel; Cloud Run via `gcloud run deploy --source .` | `requirements.txt` or `pyproject.toml`; no Dockerfile needed for Vercel or Cloud Run source deploys | Render free sleeps after 15 min and free Postgres expires after 30 days ([Render free](https://render.com/docs/free)) |

A Dockerfile is only worth generating for container hosts; Streamlit's own example exposes 8501 with a `/_stcore/health` healthcheck ([Streamlit Docker](https://docs.streamlit.io/deploy/tutorials/docker)). Fly.io no longer has a free tier for new organisations ([Fly pricing](https://docs.fly.io/about/pricing)), and Railway's free plan is $1 of usage a month ([Railway pricing](https://docs.railway.com/reference/pricing/free-trial)), so neither should be a default. For CI, GitHub's own tutorials give a one-job workflow: Python runs setup-python with pip cache, `pip install -r requirements.txt`, `ruff check` and `pytest`; Node runs setup-node with npm cache, `npm ci`, `npm run build --if-present` and `npm test` ([GitHub Docs Python CI](https://docs.github.com/en/actions/tutorials/build-and-test-code/python); [Node.js CI](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)). H.E.X should generate it from the same commands in `.hex/project.json` that the sandbox ran, pinning the Python and Node versions the mission used. The never-fabricate rule sets the wording: before GitHub runs the workflow, the handoff screen says "these commands passed in the sandbox on `<date>`", not "CI passes".

"Keep growing" follows from the same choices. Once pushed, the repo becomes the source of truth, as v0 states for its own repos ([v0 GitHub](https://v0.app/docs/github)). A later H.E.X mission on that project should start from the repo's current `main` in a fresh worktree and end in a branch and pull request, so the user's CI and branch protection act as the merge gate, which is H.E.X's apply-on-approval rule expressed in GitHub terms.

## Prioritized recommendations

The ordering puts first what removes the "it looks stale" complaint at the lowest cost, using data H.E.X already records.

| Priority | Recommendation | Rule it respects |
|---|---|---|
| 1 | Persona roster on the mission page: state icon, deterministic "now doing" line from the latest event, elapsed timer that freezes on completion, "last event N s ago" | Never fabricate: every field is a recorded event or a clock on a recorded start |
| 2 | Show setup phases and in-flight model calls as steps with live elapsed counters; no ETA or percent | Never fabricate progress |
| 3 | Plan board of milestones and features (Planned / Building / Validating / Done) that stays visible when complete, with "Done" backed by a worktree commit | Changed files come from git |
| 4 | Right-side drawer with Live / Steps / Changes / Checks, each step pairing action with git or sandbox evidence, deep-linking into the Run view | Agent claims aren't evidence |
| 5 | Collapse nine Observability tabs into a Mission view and a Developer Run view (tree, timeline, graph with shared selection, type filters, Aggregated and Expanded graph modes); hide an empty Blackboard | Shows only recorded data |
| 6 | Handoff pass: clean single commit, `.env.example`, lockfile, CI from `.hex/project.json`, Dependabot, per-stack files, README Deploy section, secret and large-file scan, user approval | User's files change only on explicit apply; keys never committed |
| 7 | Publish to GitHub via the user's `gh` login, private by default, public only on a second confirmation | Keys never reach H.E.X |
| 8 | In-app notifications on needs-input, finish and fail; queued chat messages picked up at the next feature boundary; event-built "while you were away" recap | Closed-app notifications stay deferred (D53, D57) |
| 9 | Later missions on a published project run on a branch and open a PR | Apply-on-approval extended to GitHub |

Items 6 and 7 add no new runtime dependency if `gh` is optional, but generating Dependabot and CI templates is a product decision worth recording in PRD §21. Any host deploy button (Vercel, Netlify, Render APIs) belongs to P9 and needs the user's approval before adding a dependency.

## Conclusion

The research reframes "staleness" as an evidence problem rather than an animation problem. Every product surveyed keeps users confident without ETAs; what they show is the truth at fine grain: which agent, which step, how long it has been running, and what it last touched. H.E.X's strict event log is therefore an advantage, not a constraint, provided the UI surfaces the gaps (sandbox start, a 40-second model call) that today read as silence. The one tempting shortcut, a model-written status line, is the pattern H.E.X should decline, because it would turn the agents' self-reports back into apparent evidence.

On handoff, the cloud builders' GitHub Apps are a cost of being hosted, not a best practice. A local app that pushes through the user's own `gh` login, ships CI built from the exact commands the sandbox ran, and words its claims as "passed in the sandbox" until GitHub says otherwise is both simpler and more honest than what Lovable, Bolt or v0 document. Three uncertainties remain: no source measures whether these live patterns reduce abandonment, the current major versions of `actions/setup-python` and `actions/setup-node` need checking when templates are written, and whether Cloud Run's free tier requires a linked billing account is unconfirmed.
